# גל 2 — תוכנית עבודה (השלמת עמודות, מחלקות, יחידות והערות, מי הוסיף)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Add item categories (automatic, manual override, custom per list, learned per user), units and notes, and "added by" to ShopLi. New columns on existing tables are added safely at server startup.

**Architecture:**
- The server gets `schema_upgrade.ensure_columns()` (an idempotent ADD COLUMN run at startup), a new `custom_categories` table, and new fields on items.
- The app gets a category dictionary module, a category-sorted view, and a richer edit modal and item row.

**Order:** T1 → T2 → (T3 ∥ T4 in two worktrees) → T5.

**Tech Stack:** FastAPI + SQLAlchemy + pytest. React Native 0.86 + Jest.

**Spec:** `docs/superpowers/specs/2026-11-23-improvements-round-2-design.md`. Wave 2 covers: "השלמת עמודות", items 3, 9 and 10. Plus wave-1 carry-forward: duplicate must handle categories, unit, note and added_by.

## Global Constraints
- Every global constraint from the wave 1 plan still applies: Hebrew text, no emails, the mutation guard and live refresh, TDD, lint ≤12 warnings (currently 10), line endings and BOM, local commits with no attribution.
- **Existing tables:** NEVER drop or alter existing data. New columns on existing tables are added ONLY through `ensure_columns`, are nullable, and have no server default.
- **Built-in category keys (closed set):** `produce`, `dairy`, `bakery`, `meat`, `pantry`, `frozen`, `drinks`, `snacks`, `cleaning`, `care`, `other`.
  - Their Hebrew names, in aisle order: פירות וירקות, מוצרי חלב וביצים, מאפים ולחם, בשר ודגים, יבשים ושימורים, קפואים, משקאות, חטיפים ומתוקים, ניקיון ובית, טיפוח ותינוקות, אחר.
- **Custom category value format:** `custom:<id>`.
- **Allowed units (closed set):** `יח׳`, `ק״ג`, `גרם`, `ליטר`, `חבילה`. Units are optional.
- **Lengths:** a note is ≤100 characters after trim (empty becomes NULL). A custom category name is 1–30 characters after trim, unique per list.

## Review Focus
1. Running `ensure_columns` twice, or on a fresh DB, must be a no-op. It must never lose data.
2. A custom category from list A must never be accepted for, or shown on, list B. That includes duplicate and learning.
3. Deleting a custom category leaves no item or history row pointing to it.
4. A manual category choice survives live refresh, and survives other members' edits of other fields.
5. "נוסף ע״י" never shows for the current user's own items, never shows emails, and survives the adder's account deletion (it becomes NULL, not an error).

### Task T2: Categories, custom categories, learning, and duplicate carry-forward (server)

**Files:** Modify `main.py`, `models.py`. Create `tests/test_categories.py`. Modify `tests/test_duplicate.py`.

**Interfaces:**
- Produces:
  - **New table** `models.CustomCategory` (`custom_categories`): `id`, `list_id` (FK; cascade delete with the list via `ShoppingList.custom_categories`), `name`, `color`, `created_at`. `UniqueConstraint(list_id, name)`.
  - **`GET /lists/{id}/categories`** returns `[{id, name, color}]` in creation order.
  - **`POST /lists/{id}/categories`** takes `{name}` and returns `{id, name, color}`.
    - It returns 201.
    - A duplicate name in the same list gets 400 "המחלקה כבר קיימת ברשימה".
    - The color is assigned from the palette `["#8E44AD","#16A085","#D35400","#2C3E50","#C0392B","#7F8C8D","#27AE60","#2980B9"]`, picking the first unused one, then cycling.
  - **`DELETE /lists/{id}/categories/{cat_id}`:**
    - Sets `items.category=NULL` where it equals `custom:<cat_id>`.
    - Sets `item_history.category=NULL` where it equals `custom:<cat_id>`.
    - Deletes the category.
  - **Access:** all three require owner or member. A stranger gets 403 and a missing list gets 404, with the existing Hebrew messages. A category of another list gets 404 "המחלקה לא נמצאה".
  - **`ItemCreate` / `ItemUpdate`** get an optional `category: Optional[str]`.
    - The value is valid if it's null, a built-in key, or `custom:<id>` where the custom category belongs to the item's list. Anything else gets 400 "מחלקה לא תקינה".
    - In `ItemUpdate`, sending `"category": null` explicitly resets it to automatic. Use `model_fields_set` to tell "absent" from "null".
  - **Learning:**
    - When `PUT /items/{id}` sets `category` (present in the body), upsert the current user's `item_history` row for that item's name with `category` set to that value (null clears it).
    - When `POST /items` has no category in the body and the user's history for that `name_key` has a category, apply it — only if it's a built-in key, or a `custom:<id>` that belongs to THIS list.
  - **Responses:** items in `GET /items`, `POST /items` and `PUT /items` now include `category`.
  - **Duplicate** (`POST /lists/{id}/duplicate`):
    - Copy the source list's custom categories into the new list, which gets new ids.
    - Remap each item's `custom:<old>` to `custom:<new>`.
    - Copy built-in categories as-is.
- [ ] **Step 1: Failing tests.**
  - CRUD, with the color assignment and the duplicate-name 400.
  - Access: a member can, a stranger gets 403, and the other list's category gets 404.
  - Validation: a built-in key is accepted; a bogus key gets 400; another list's `custom:` gets 400.
  - Explicit null resets the category.
  - Learning:
    - a built-in category learned across lists
    - a custom category learned only within the same list
  - Delete nulls items and history.
  - Duplicate remaps the custom categories, and the source is unchanged.
- [ ] **Step 2:** Run → FAIL.
- [ ] **Step 3:** Implement.
- [ ] **Step 4:** Full pytest → PASS.
- [ ] **Step 5:** Commit: `Item categories: custom per list, manual override, learning (server)`

  - `src/screens/ShoppingListScreen/ShoppingListScreen.js` (+ styles)

**Interfaces:**
- Consumes: the T2 endpoints.
- Produces:
  - **`categories.js`:**
    - `BUILTIN_CATEGORIES`: an ordered array of `{key, name, color}` for the 11 categories.
    - `categorize(name) -> key`: whole-word or contained-word matching on a Hebrew keyword dictionary, with at least 15 common products per category. The longest keyword match wins. The default is `'other'`.
    - `resolveCategory(item, customCategories) -> {key, name, color, order}`:
      - `item.category` if it's set and valid for this list's custom categories;
      - else `categorize(item.name)`;
      - a dangling `custom:` reference falls back to automatic.
      - The order is: built-ins first, then customs in creation order, then "אחר" last.
  - **`api.js`:** `getListCategories(listId)`, `createListCategory(listId, name)`, `deleteListCategory(listId, catId)`. `updateItem` already passes arbitrary fields.
  - **`EditItemModal`:**
    - A "מחלקה" chip row with: "אוטומטי" (sends `category: null`), the built-ins, the list's customs, and "+ מחלקה חדשה". The last one shows a small inline input: create it, then select it.
    - A long-press on a custom chip shows a confirmation Alert, then deletes the category.
    - `onSave` now sends `{name, category}`.
  - **`ShoppingListItem`:** shows a color dot from `resolveCategory`. The existing `categoryColor` slot is fed by the screen.
  - **The screen:**
    - Loads the categories on mount, on refresh, and after create or delete.
    - A toggle "סדר ידני / לפי מחלקות" (`testID="sort_mode_toggle"`), persisted per list in AsyncStorage under the key `@sort_mode_<listId>`.
    - In category mode, the unpurchased items are grouped under section headers (`testID="category_header_<key>"`) in category order, and dragging is disabled.
    - All mutations go through the guard.
